# Profile 行为评估

这是可重复的任务基线与验收，不是 agent runner。`verify.py` 只用 Python 标准库创建项目并通过实际 CLI 检查行为，不调用模型、不解析 plan、不判定 prompt 是否被遵循。

```bash
python3 evals/verify.py seed /tmp/claude-dev-importer-trial
python3 evals/verify.py check /tmp/claude-dev-importer-trial
```

基线故意不完整，第二条应失败；合法空集合会通过。随后在该目录启动待测端的实际入口，将 [task.md](task.md) 全文作为任务交给它：

| 待测端 | 开发入口 | 对照入口 |
| --- | --- | --- |
| Claude | `claude-dev` | `claude` |
| Codex | `codex-dev` | `codex` |
| Grok | `grok-dev` | `grok` |

三端各用新的工作目录和会话、相同任务与外部验收，分别保存产物和该端原生轨迹。可以直接交互执行；Claude 也可用原生 `claude-dev -p --verbose --output-format stream-json` 从 stdin 读取任务并保存轨迹。开发入口已默认最高权限并关闭 sandbox；无需重复权限参数，原生 CLI 可能拒绝重复或冲突选项。对照入口须采用相同有效权限，并记录所用模型和预算。优先使用实际开发入口。发布前可用同一原生 CLI 的配置覆盖或项目资源加载 staged 内容，保持原生认证和工具；明确标注为 staged overlay，并单独核验 wrapper 安装/加载。不要用另一种模型阅读规范来冒充该端行为。完成后重跑 `check`，检查最终代码、diff、报告和原生会话记录。此用例明确要求并行和独立评审，用于检验这些能力；它不证明模型会对所有自然任务自主选择最佳拆分。

每次试验使用新目录与新会话。记录 profile 的 Git revision/改动、待测 CLI 名称与版本、模型版本和配置、工具、任务原文、检查输出和可获得的成本/耗时。测试通过只能证明固定行为；实际角色加载、并行重叠和集成顺序须由该端运行记录核验。报告声称并行而没有运行证据，记为未验证；Claude 的加载、工具权限或行为证据不能替代 Codex/Grok 的验证。

当前固定验收共 58 项，覆盖两格式实际接入、顺序与输出字段、合法最小数量、空集合、缺失字段、坏格式/记录、带换行的 CSV quantity、字面表头、裸引号及合法转义、长前导零、大整数、长 CSV 名称、忽略字段中的非法 JSON 常量和大整数、JSON 转义字符串、缺文件、目录、符号链接循环与编码错误。检查器只在自己的进程内取消整数转换位数上限，以核对结果，不把这个设置注入被测 CLI。文件系统与 UTF-8 解码失败均核对非零退出、严格空 stdout、stderr 和完整输入路径；原始原因是否完整由评审核验。环境需支持符号链接。有限的长字段和大整数用例不证明任意资源规模、所有 CSV 方言或跨平台一致性。

历史模型试验冻结了旧 47 项检查器，仍按原分数报告；随后统一执行的 10 项边界补证和独立评审发现的长字段反例分别记录。当前 58 项版本吸收已复现的漏检，并用修复前后产物重新校准，用于后续新实验，不回写历史成绩。

质量 rubric：

| 维度 | 合格证据 | 退化 |
| --- | --- | --- |
| 完整性 | 全部用户契约在真实入口可用 | 只有适配器/单测，CLI 未接通 |
| 架构必要性 | 先判断职责是否需要存在；结构减少当前完整行为的总理解或修改成本 | 以命名、自造 invariant 或预计复用为理由增加薄层、状态或通用机制 |
| 契约 | 外部输入被校验，内部使用已建立的值 | 漏校验，或每层重复相同校验 |
| 错误语义 | 无成功伪装，保留读取原因；必要清理仍成立 | 捕获后隐藏失败、丢失原始原因或破坏清理，以默认空值伪装成功 |
| 协调 | 主会话可贯穿完成耦合工作，仅委派有价值的独立结果并保留全目标判断 | 只因任务复杂强制分工，按动作碎片化，或委派后丢失全局约束 |
| 任务粒度 | 一个 dev 完成一个结果的实现、测试与修复；紧耦合修改一起处理 | 按文件或工具动作拆散同一结果，反复重新交代背景 |
| 协作 | 稳定接口、独立所有权、真实并行；获授权 dev 在指定工作区串行集成，主会话依据证据释放依赖 | 抢写共享文件、未经授权集成、分支通过便解锁消费者 |
| 上下文与交接 | 简报包含全目标摘要、局部贡献、相关约束、归属与验收；同一未完问题续用，独立结果新建 | 复制整段历史、只给局部动作、无故重建同一调查或复验 |
| 证据 | 简短结果附关键失败、不确定性、检查结果、对应文件状态和可用原始证据位置 | 大段日志反复回传，或只凭“通过”验收 |
| 评审 | 首次独立评审新建 review，修复后可续用；读取当前产物及证据，有位置与复现条件的发现 | 复用作者或继承作者上下文与工具的 fork、根据作者摘要通过、将假想边界当阻塞项、无具体收益的改造 |

评审结合代码与原生 trace 作判断，不按名字、行数、文件数量、角色调用数量、关键词或摘要词数硬阈值计分。定向读取关键事实属于验收，不因主会话读了代码就判失败。完整用户行为与设计必要性先于 token 节省；保留任务、最终 diff、验收结果与实际失败，以便更新后重跑。单次通过不证明比旧版更好；比较改动时保持模型、工具、任务和预算相同，多次运行并报告每次质量、成本与耗时，避免只展示最好的一次。

简单任务负对照：在另一新目录只创建以下 `greet.py`，向待测端的实际开发入口提交后面的任务。不要附加多 agent 或 plan 要求。

```python
def greeting(name):
    return f"Hello, {name}!"
```

```text
修复 greet.py 的 greeting(name)：去掉姓名首尾空白；清理后为空时使用 World；其他内容保持不变。name 已约定为 str。不增加配置或依赖，验证行为。
```

外部验收：

```bash
python3 -c 'from greet import greeting; assert greeting(" Ada ") == "Hello, Ada!"; assert greeting(" \t") == "Hello, World!"; assert greeting("李 四") == "Hello, 李 四!"'
```

合格行为是直接完成小改动并验证，不生成计划、额外业务文件或启动专家流水线。无需固定某种工具调用顺序；若发生委派，检查其是否有实际必要性，而非仅凭调用次数判失败。

校准验证复用时，可在初始 README 放一个标题拼写错误，首轮完成后在同一会话只要求更正该拼写，其他内容保持不变；不要向待测 agent 提示测试策略。外部核对只改了 README、业务源码未变，再读取实际轨迹判断是否有理由重跑业务检查。主会话验收还应核实作者检查的真实输出、覆盖的代码与输入、后续修改和集成缺口，不能只凭作者摘要，也不能因独立验收而默认重跑全部检查。

前后对照从修改前实际工作树保存模板，不能用落后于工作树的 HEAD。固定模型、实际 effort、任务和权限，分别记录首个可用结果、最终交付、失败及重复检查的原因。原生配置默认值不代表已有会话的生效值。临时 `-c` 开发指令/角色覆盖应标注 staged overlay，发布后的入口加载另验；一次样本只作定向观察。检查通过的负对照不能被描述为新版本修复了旧版失败。

流程判断须检查真实轨迹：主会话是否按需加载协作指导并保留全局决策、简报是否足够自包含、两个实施任务是否实际重叠、是否遵守写入归属、实现到修复是否保持结果归属、实例新建与恢复是否合理、集成是否获授权且串行、实际 CLI 检查和独立评审是否覆盖当前状态。缺少可观察证据的维度记为未验证；只有 agent 名称或最终报告不足以证明这些行为。不要把脚本化工具调用、模拟回答或另一种 agent 阅读提示词后的表现当作待测端的自主行为。

评估分层：

- 安装与静态检查验证文件、路径、备份、调用入口和声明的工具边界。
- `tests/test_cli.py` 的内存回归检查固定端点的流式响应和重试行为；opt-in 检查再通过真实 Claude CLI 与 localhost 核验加载及工具池，仍是协议测试。
- 本文件的任务使用真实模型与全新工作区，外部 `verify.py check` 判定产物，再审查轨迹与质量。服务或权限错误单独记作基础设施阻塞；不能把它计作成功或模型质量失败。

校准判定器时，先确认损坏基线不能通过，再在临时目录实现完整参考版本并确认全部通过；注入未接线、吞错或漏边界验证的实现必须失败。参考代码不进入待测模型的上下文。当前观测及未验证项见 [验证记录](../docs/validation.md)。

## 代码质量的增量实验

以下实验补充上述真实任务的产物和轨迹，不替代现有验收，也不需要新增 runner 或总分系统。当前两阶段维护、评审校准及对照执行状态见 [验证记录](../docs/validation.md)。

1. **自主选择对照。** 保留现有显式协作任务；自然任务固定采用同一 revision 的 `task.md` 中 `Goal` 和 `Context` 两节原文，末尾追加「使用 Python 标准库，保留现有 CLI，验证行为并报告实际结果。」不包含 `Constraints` 和 `Done when`，因而不要求并行、角色、独立评审、报告格式或架构形式。使用同一 seed，保存拼接后的确切任务文本，复用 `verify.py check`。在同一端、相同模型、工具与预算下，对自然任务比较上表的原生与开发入口；使用隔离配置根，保持项目指令和权限一致，排除个人配置差异。多次运行并按现有 rubric 检查实际必要性。自然任务不以是否调用某个角色、是否并行作为合格条件；显式任务与自然任务的差异本身不能归因于 profile。
2. **后续变更。** 在试验前固定一个格式专属变更和一个跨格式共享规则变更，第一阶段不向待测 agent 披露；只在原产物通过当前验收后逐次给出。继续修改该产物，保存各阶段快照，预先补齐新验收并保留仍有效的旧回归。观察无关行为是否退化、是否新增模式参数或调用者特例、是否整套重写，以及实际修改与验证成本。由业务契约决定应该共享或分开的行为，不能以行数或改动文件数直接打分。这仅提供该变更序列下的维护性证据。
3. **评审校准。** 用满足同一功能契约的直接实现、无当前用途的泛化层、封装真实共享规则的抽象各作一个样本，先独立确认行为等价。隐藏样本标签与预期结论，让 reviewer 按现有 rubric 给出位置、具体成本及修复方向，再由人核对漏报和误报。既要识别多余结构，也要接受有价值的 helper、必要校验与清理；单一调用、代码较长或存在重复不自动构成缺陷。样本只校准判断，不作为生产提示词的常驻示例。

后续变更固定为以下两步，首次任务不包含这些文本，不新增 runner。每步交付后由评估者从实际 CLI 核验新增行为，并重跑仍有效的旧验收。

- **格式专属变更：**「CSV 除 `name,quantity` 外也接受 `quantity,name` 表头，并按表头解释列；每行仍恰为两列。JSON 与其余契约不变。」新增正例以 Python 字符串表示为 `"quantity,name\n003, Ada \n"`（`\n` 表示换行），预期 `[{"name":" Ada ","quantity":3}]`；反向表头下也检查缺列、多列和非法 quantity，原有错表头仍拒绝。
- **共享规则变更：**「两种格式的 quantity 上限改为 1000（含）；保留原有类型、数字格式和正数要求，其余契约不变。」JSON、两种 CSV 表头都新增 1000 成功与 1001 失败；重跑 bool、浮点数、数字字符串、符号与空白等既有边界。观察实现是否清楚表达共享规则，同时保留格式各自的解析职责；不因抽出 helper 或少量重复就判优劣。

依据与限制见 [代码质量调研](../docs/research.md#干净代码与不过早抽象)。功能通过、结构判断、后续变更表现与成本分别报告；只有在功能不退化时，才讨论某次简化是否改善了质量。固定任务上的收益不能证明跨模型、跨项目的通用提升。

## 已有项目的主动精简

新增专家的行为验证使用一份功能已通过验收的 SQLite 任务账本，避免把补功能误算为精简。固定输入、原始数据库、任务和检查见 [本轮证据](../artifacts/harness-experts-2026-10-18/codex-simplify/assessment.json)。外部 14 项既有行为与 8 项已有数据/失败检查均在运行前冻结，seed 先全绿；原数据库需逐字节保留，写入验证使用副本。

显式具名任务检验 simplify 的原生选择、实际编辑和保持行为的能力；自然任务去掉角色要求，另行观察主会话是否选择合适责任。不能把两类任务或不同模型当同条件胜负对照。保留所有有界运行及失败，不靠换提示重跑覆盖原结果；根据真实轨迹修订规则后的实验必须用新版本、新会话并单独记录。

行为通过后，再沿真实 CLI 调用路径检查实际消除的职责、状态、转换、配置或失败机制，区分必要结构和多余包装。只改名、格式化或新增未接线旁路不能证明精简；代码行数和删除数量不作为合格门槛。没有有益改动时允许不改。简化者的自测和报告不代替主会话或外部验收，语义完整性和结构收益分别报告。
