# 设计

本项目是在三个原生 harness 之上的个人开发偏好配置：用一致的质量取舍和少量原生角色表达简洁、干净、优雅的目标，运行机制由原生客户端负责。目标是经过必要调查权衡，用最小维护面积完成完整用户行为。质量取舍优先约束职责、状态、数据流与错误语义，编排只在能解决实际问题时使用。[调研](research.md)区分来源与本项目判断，[验证](validation.md)记录实际证据。

## 质量与职责

用户要求和真实接口/数据契约是依据。计划、架构文档和测试不会使 agent 自定的内部机制永久化；可依据原要求重选设计和修正过度规定的检查，不能通过削弱真实行为或隐藏失败获得通过。

增加抽象前先判断其责任能否取消或直接表达。抽象须减少当前使用的整体理解/修改成本；命名、预计复用和自造 invariant 不够。允许局部重复，优先标准库、平台内置及已有合适能力，狭窄当前需求可直接自实现；第三方的功能或实现难度收益须足以抵消集成与维护成本，小实现不扩成通用框架。这项偏好写入根规则及每个子角色，避免独立上下文丢失，也不要求为零依赖替换现有合适能力。少错误处理通过减少失败机制、信任内部契约和让未知错误原样传播实现；不在没有当前合同时猜测、转换或修复未支持输入，不额外枚举校验。必要边界校验、清理和失败呈现继续成立。只对反直觉原因与必要取舍注释 why。

| 组成 | 责任 | 使用边界 |
| --- | --- | --- |
| 根规则 | 质量取舍、原生路由和完整交付 | 常驻；不复制研究全文或项目地图 |
| 主会话 | 全目标、设计决策、直接实施、必要分工和最终交付 | 耦合工作可贯穿完成，不因复杂或跨文件被迫只做管理 |
| research | 本轮需求、现有合同与决策相关未知 | 一手证据足够即返回；必要用户问题交主会话，不扩功能 |
| arch | 当前用途的最直接完整设计 | 复用研究，只定义当前接口；后续证据可推翻提案 |
| dev | 一个结果的实现、持续简化、交付前自查、检查与修复 | 自查清理属于同一实现任务；保留有益结构与局部重复，无强制改动配额 |
| simplify | 独立接管可用实现并实际精简 | 可删改内部架构，保留真实行为和数据；无改动配额 |
| review | 行为正确性与整体设计必要性 | 具体风险时独立评审；先判断保证是否需要，再查实现 |
| develop | 项目路线、主动简化、依赖交接与恢复 | 项目目标、实质简化、协调或恢复时按需读取 |

## 协作、反馈与终点

粗略 goal 先收敛为当前用户路径、必要功能和可观察的完成条件。只向用户确认会改变功能、使用方式或数据的疑问，普通技术取舍自主完成；不预建未来功能和扩展。默认先尽早贯通最简单完整路径，由作者自清理、必要验证后交付。调研、架构、独立精简和评审只为具体未知、复杂度或重要风险启用；项目大小不自动增加阶段。已有可靠结论直接复用，只有新证据才重开已解决的决定。

必要产品问题是相应实现的依赖：等待用户回答后再实施该部分，同时继续不依赖答案的工作。不能在提出问题后自行扩功能或选择尚未确定的使用方式。这不把日常技术取舍转交用户，也不增加阶段审批。

主会话可以直接调查、设计、实施和验证。独立研究、有稳定输入的实施结果或有价值的新视角才委派；不按文件数、角色数或工具动作拆任务。耦合实现、自查精简、测试和修复由一个 owner 持有。交付前作者沿真实路径复查自己的改动，直接实施有益清理后核验受影响行为；主会话直接实施时也适用。明确的精简目标或具体结构问题才需要独立 simplify 的新判断，不替代作者对基本质量负责。独立结果可并行，共享接口、lockfile、运行服务和集成各有明确归属。

依赖图只回答当前什么可做、何时可消费结果；原生 loop 根据实际结果选择下一动作。主会话核实实际集成代码和检查输出，复用仍覆盖当前代码、输入和环境的结果，只补缺失或失效的检查。无关改动或二进制变化本身不要求重跑全部测试或性能矩阵，明确项目/发布门禁仍然有效。失败依据实际错误或当前状态调整下一步，不重复失效假设。普通编辑、编译、列测试和运行测试之间不另造审批、快照或证据冻结链。

simplify 有与 dev 相同的编辑和执行能力，以新的独立上下文沿真实入口检查整个分配范围，可以删除、内联、合并或替换子系统。已有项目先识别真实消费者与持久数据，再按可运行、可验证的批次精简。决定委派时，直接把完整范围交给 simplify，由它调查、修改、验证和修复；主会话不先重复完整调查，也不强插一次开发阶段。小而明确的清理可由当前 owner 直接完成，独立结构重评用于具体复杂度或整体精简目标。基线保护真实合同，不把所有偶然实现细节钉死。需要独立精简时，开发者先完成可用路径并停止相关写入，简化者接管该范围及其检查修复；禁止并发重写耦合实现。未获授权不能为精简删除使用中的功能或改变真实数据合同。

整项目精简先比较完整分配范围与满足当前用途的最直接实现，找出最大的可取消职责，再选择工作。旧调用者、设计和测试只能说明机制存在，不能单独证明它属于当前需求。主会话按具体产品或架构结果验收，不能把第一个通过检查的局部清理当作整体完成；不另设文档、阶段或重写配额。

独立简化者也是作者，其报告不能代替最终验收；主会话可复用有实际输出且覆盖当前状态的作者检查，确认集成缺口，具体重要风险再用只读 review。没有有益简化时允许不改，不能为了留下 diff 或删行指标重写。

review 不以潜在 hardening、未来扩展或额外测试自动阻塞交付；没有实质问题时可接受当前直接设计。维护简洁与行为完整同时成立，不能为少行数压成难读代码或删掉必要能力。本轮功能完整、作者自清理且相关检查通过即交付；不能用进度汇报或宣布下一步代替推进仍可做的授权工作，交付前要收取必需的后台命令和 worker 结果。已知的必需功能失败或数据完整性问题要修复；未知 bug 不构成再开审计、hardening 或清理轮的理由。开放质量偏好不要求证明全局最优，后续需求和使用中发现的问题另行迭代。

长任务仅留一份恢复所需的目标、决定、剩余工作、证据位置和活动句柄。恢复时核当前文件与原生句柄，观察超时不等于进程已结束。相同失败没有新证据则改变诊断，不重复同样动作，也不启动冲突写者。自行创建的 scratch 和检查 fixtures 服从分配写入范围，使用唯一位置，只清理本任务创建的内容。

## 三端权限与上下文

Claude 使用原生 Markdown 角色和 tools 白名单，review 只有 Read/Grep/Glob。Codex 子角色继承父权限；只读、本地证据与不再派发是行为约定，不能宣称 TOML 角色拥有独立只读沙箱。五个角色继承原生模型与 effort，不默认新增运行策略。

Grok 使用原生角色 Markdown。已核读的随包及官方仓库文档支持 spawn_subagent 的 subagent_type；按运行时 schema 优先直接具名派发，只有缺少该选择器时用原生 Workflow agent_type。旧 1.0.41 的 Workflow 探针属于历史证据，不用于推断当前直接派发的实际子工具集。research/arch/review 保留 tools、disallowedTools 与 mcpInheritance 声明；非空父 MCP 过滤及当前实际子工具仍按运行证据判定。

Codex/Grok 的子角色各保留一段共同质量合同，避免角色载入替换或不继承父 developer/--rules 时丢失关键偏好。任务简报携带完整目标摘要、局部结果、相关约束、输入、归属和验收。独立任务使用独立上下文，同一问题的修复优先延续；原生 successor、run handle 与 child ID 各按实际语义使用。Workflow 完成不自动证明每个 child 成功。

## 安装边界

`./install.sh [--target claude|codex|grok|all] [--home DIR]` 使用 Bun 发布原生资源，默认选择 Claude。Claude 保持原有配置根；Codex/Grok 在普通配置之上添加开发规则，不再切换整个配置根。

| 入口 | 实现 | 受管内容 |
| --- | --- | --- |
| Claude | 设置 CLAUDE_CONFIG_DIR，`exec claude --permission-mode bypassPermissions --settings '{"sandbox":{"enabled":false}}' "$@"` | `.claude-dev` 中的根规则、角色、skills |
| Codex | `exec codex --profile dev --dangerously-bypass-approvals-and-sandbox "$@"` | `.codex/dev.config.toml` 与 `.codex-dev` 中的根规则、角色、工作流 |
| Grok | 读取规则，`exec grok --rules "$rules" --permission-mode bypassPermissions --sandbox off "$@"` | `.grok-dev` 中的根规则、工作流，以及 `.grok/agents` 中的五个角色文件 |

三个入口按用户要求默认使用原生最高权限，并关闭各 CLI 的独立内置 sandbox。Claude 的权限模式与 Bash sandbox 是两个设置；Grok 的审批模式与进程 sandbox 也独立，因此分别传入参数。固定参数放在用户参数之前，用户参数原样传递，重复与冲突遵循各原生 CLI 的行为；不增加参数解析器或覆盖外部 OS、组织策略和原生强制规则。`exec` 保留进程、信号和退出状态语义，模型与 effort 继续使用原生配置和用户参数。

Codex 的 profile 生成 developer_instructions 和五项原生角色注册，角色 config_file 使用绝对路径；升级时保留已有顶层 model/model_reasoning_effort 字符串，不新增默认值，也不合并其他手写字段。未在 profile 选择的模型、provider、认证后端及其他运行设置继续原生继承。wrapper 的权限参数只覆盖当前运行的审批和 sandbox，profile 的 developer_instructions 覆盖基础配置的同名字符串。不会设置替换原生基础提示词的 model_instructions_file。原生 profile 不支持 login、logout、app-server 等所有管理命令，因此这些命令使用普通 codex，wrapper 不复制原生参数解析器。

Codex 角色的 developer_instructions 又会覆盖主会话的同名字段。因此五个角色各自保留一段简短质量合同，避免改用 profile 后丢失原本由用户 AGENTS 提供的共同原则；不将主会话的调度职责复制给子 agent。这段有明确用途的重复比增加安装时提示词分段与拼接机制更直接。

Grok 的 --rules 在原生主会话提示词上追加开发正文。真实具名 review 子会话没有继承这段根规则，因此五个角色也各自保留与 Codex 相同的简短质量合同，覆盖真实契约、抽象必要性、信任边界、真实错误与适度验证；任务专属约束仍由简报提供，不复制主会话调度职责，也不增加安装时拼接器。wrapper 读取失败即停止，不会将读取失败静默变为空规则。角色逐个发布到用户 agents 目录，普通安装不覆盖其他角色；普通 grok 也能发现新增的五个角色。无需生成或重写 Grok config.toml，也不发布固定 Workflow 脚本。

两端不再需要凭证共享选项、链接或启动同步。普通与开发入口使用相同原生配置根，自然遵循相同账号状态；安装器不验证账号是否仍有效，也不读写认证。旧 `.codex-dev` 和 `.grok-dev` 中的配置、认证及历史保留，更新后的入口不再将其选为原生配置根。旧认证链接也保持原样，无需先删除才能迁移。

三个客户端分别使用少量原生模板，共用发布机制，不建立模板编译框架。Claude develop 是原生 skill；Codex/Grok develop 是常驻开发规则指向绝对路径的私有工作流，协调与恢复时读取，不注册全局 skill。Codex 发布模板中的工作流子目录并保留旧资源根的 skills/.system；Claude/Grok 的受管 skills 目录整体同步。受管文件或目录变化前完整备份，相同内容不重写；不要在受管单元里添加个人配置。

`--home` 指定安装与清理目标，不更改进程 HOME。Codex/Grok 只发布到目标 HOME 下的标准原生目录；安装环境中选中端的非空 CODEX_HOME/GROK_HOME 若指向别处，在发布前报错，不增加跨根迁移与备份机制。运行 wrapper 时仍服从原生 HOME 选择，更换 HOME 或自定义配置根需要在新根准备 profile 与角色。临时安装的测试同时使用临时运行 HOME。

`CLAUDE_CONFIG_DIR` 改变用户配置根，但项目指令仍沿祖先目录加载；项目位于 HOME 下时，默认 `.claude` 的指令可能再次进入会话。安装器因此只在 Claude profile 的 settings.json 中拥有一条 claudeMdExcludes 排除项。它保留其他键与已有排除项，变更前备份原始文件及权限；所需项已存在则不重写。排除路径基于安装进程 HOME，独立于 --home 发布目录。glob 字符按字面匹配；原生匹配器将反斜杠归一化为分隔符，故拒绝包含反斜杠的 HOME。排除只控制指令自动加载，不限制文件读取，也不排除项目指令。

Codex/Grok 仍会加载原生全局与项目指令，以及各自支持的共享扩展目录。普通安装保留这些来源；显式 `--target all --clean-legacy` 才将已知位置的旧用户指令和扩展移入备份。Grok 新管理的五个角色必须同时保留，连续清理安装也应幂等。直接发现的旧插件按原生 manifest 或组件标记识别；缓存和数据保留。不改项目配置、认证、会话、CLI 二进制或原生分发资源。

清理模式移除全局 MCP，以及 Claude JSON 中的 hooks 和用户插件注册。TOML 只清理 MCP，使用对应原生 CLI 在临时副本中修改，并对非目标字段作语义比较；其他 hooks、扩展发现配置和任意自定义路径不在清理范围。全部准备和预检先于发布；失败不输出配置内容。--dry-run 使用同一准备逻辑，只报告路径，不修改目标 HOME。

源资源拒绝符号链接和特殊文件；目标路径与备份位置在发布前检查。备份用于恢复，安装不声称具备跨路径事务或进程间锁。只在无并发安装时执行。

## 明确舍弃的机制

- 外层 supervisor、常驻 scheduler、默认 Stop hook：原生会话与子 agent 已承担运行职责，通用 profile 没有可机械判断所有项目完成的命令。
- 实验性 teams 和图框架：当前需求是有界委派和协调集成，不需要持续点对点团队通信或持久执行引擎。
- 强制角色流水线、唯一计划 schema、通用跨端转换器：三个实际客户端各维护少量原生内容，共用发布机制即可。
- 模型别名重写、固定 effort/压缩参数：这些运行策略交给各原生 CLI；wrapper 只选择开发资源并设置默认最高权限，不复制 CLI 解析器。
- 技能编写和微信搜索：它们是独立工作能力，不属于此开发 profile 的默认内容。

提示词指导决策，原生工具控制能力，项目检查证明行为。三者各有边界，不能互相替代。
